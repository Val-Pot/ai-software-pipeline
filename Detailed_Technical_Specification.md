# Детальное Техническое Задание (MVP)
## Минимально жизнеспособный прототип (MVP) интеграции Telegram, GitHub Copilot Coding Agent и GitHub Actions

**Версия документа:** 1.1  
**Дата:** 7 августа 2026 г.  
**Статус:** Согласование прототипа (MVP)  
**Язык:** Русский  

---

## 1. Назначение системы (Purpose)

Настоящая система представляет собой **минимально жизнеспособный прототип (MVP)**, предназначенный исключительно для **проверки и валидации гипотезы интеграции Telegram, GitHub Copilot Coding Agent и GitHub Actions**.

Основная цель прототипа — продемонстрировать техническую возможность передачи текстового описания задачи из Telegram в GitHub Issue, назначения задачи на GitHub Copilot Coding Agent, получения вопросов и ответов от агента, отслеживания результатов автоматического тестирования в GitHub Actions и отправки итогового статуса пользователю.

---

## 2. Область применения и границы (Scope)

### 2.1. Входит в область MVP:
1. Прием текстового описания задачи от авторизованных пользователей через Telegram Bot.
2. Создание GitHub Issue в целевом репозитории.
3. Назначение задачи на агента `github-copilot[bot]`.
4. Отслеживание состояния работы агента (старт, вопросы агента, открытие Pull Request).
5. Передача уточняющих вопросов от Copilot пользователю в Telegram и отправка ответов пользователя в комментарии GitHub Issue.
6. Отслеживание статуса запусков GitHub Actions (`workflow_run`) для открытого PR.
7. Автоматический перезапуск генерации кода агентом при падении CI-тестов (публикация команды `@copilot fix the failing tests`).
8. Опциональная (Optional) возможность вызова AI-ревью кода.
9. Отправка уведомления пользователю в Telegram о финальном результате с ссылкой на PR.

### 2.2. Не входит в область MVP (Out of Scope):
- Промышленная эксплуатация и интеграция с корпоративными системами.
- Мульти-репозиторная работа (поддерживается 1 репозиторий).
- Мульти-агентная работа (поддерживается 1 AI-агент).
- Автоматическая оплата или биллинг.
- Гарантии отказоустойчивости промышленного уровня.
- База знаний (Knowledge Base).
- Граф агентов (LangGraph).
- Retrieval-Augmented Generation (RAG).
- Распределённое выполнение.

## 3. Функциональные требования (Functional Requirements)

### FR-1: Прием задачи в Telegram
- **FR-1.1**: Система предоставляет пользователю возможность инициировать новую задачу через специальную команду в Telegram Bot.
- **FR-1.2**: Система проверяет, что пользователь входит в список авторизованных Telegram ID.
- **FR-1.3**: Система запрашивает у пользователя подтверждение перед созданием задачи.

### FR-2: Отслеживание состояния задачи
- **FR-2.1**: Система отслеживает текущее состояние каждой активной задачи на всём протяжении пайплайна.
- **FR-2.2**: Пользователь имеет возможность запросить текущее состояние задачи через Telegram.
- **FR-2.3**: Пользователь имеет возможность отменить активную задачу через Telegram.

### FR-3: Интеграция с GitHub и Copilot Agent
- **FR-3.1**: Система создаёт Issue в целевом репозитории GitHub с описанием задачи из Telegram.
- **FR-3.2**: Система назначает созданную Issue на `github-copilot[bot]`.
- **FR-3.3**: Система обнаруживает уточняющие вопросы от Copilot в комментариях к Issue и доставляет их пользователю в Telegram.
- **FR-3.4**: Система отправляет ответ пользователя из Telegram в комментарии к Issue на GitHub.
- **FR-3.5**: Система фиксирует факт открытия Pull Request агентом и сохраняет ссылку на PR.

### FR-4: Интеграция с GitHub Actions
- **FR-4.1**: Система принимает вебхуки от GitHub с событиями `workflow_run`.
- **FR-4.2**: При получении события о провале тестов система публикует команду `@copilot fix the failing tests` с фрагментом лога ошибки.
- **FR-4.3**: Система ограничивает максимальное количество итераций автоматического исправления.

### FR-5: Уведомление пользователя
- **FR-5.1**: После успешного завершения пайплайна система отправляет пользователю в Telegram итоговое сообщение со ссылкой на Pull Request и его статусом.
- **FR-5.2**: При получении вопроса от Copilot система немедленно уведомляет пользователя в Telegram.

## 4. Нефункциональные требования (Non-Functional Requirements)

- **NFR-1**: Система должна отвечать на входящие вебхуки в пределах, установленных стандартом HTTP (ответ 200 OK), без блокирующей обработки.
- **NFR-2**: Обработка вебхуков должна быть идемпотентной — повторная доставка одного и того же события не должна вызывать двойного действия.
- **NFR-3**: Система должна поддерживать асинхронную обработку событий.
- **NFR-4**: Система должна быть пригодна для локального развёртывания и проверки с помощью контейнеризации.
- **NFR-5**: Взаимодействие с API GitHub должно производиться с проверкой подлинности входящих запросов по цифровой подписи.

---

## 5. Логические компоненты системы

Система состоит из следующих логических компонентов:

1. **Интерфейс пользователя (Telegram Bot)**: Компонент приёма задач, команд пользователя и отправки уведомлений.
2. **Оркестратор пайплайна**: Компонент управления состоянием задачи и координации остальных компонентов.
3. **Компонент GitHub**: Компонент взаимодействия с GitHub REST API и приёма входящих вебхуков.
4. **Компонент Coding Agent**: Компонент обработки логики взаимодействия с `github-copilot[bot]`.
5. **Компонент GitHub Actions**: Компонент обработки событий CI-пайплайна.

---

## 6. Конфигурация системы

Система должна допускать настройку через переменные окружения:

- `TELEGRAM_BOT_TOKEN`: Токен Telegram-бота.
- `TELEGRAM_ALLOWED_USER_IDS`: Список идентификаторов авторизованных пользователей.
- `GITHUB_TOKEN`: Токен доступа к GitHub API.
- `GITHUB_OWNER`: Владелец целевого репозитория.
- `GITHUB_REPO`: Имя целевого репозитория.
- `GITHUB_WEBHOOK_SECRET`: Секретный ключ для проверки подлинности вебхуков GitHub.
- `COPILOT_USERNAME`: Идентификатор учётной записи Copilot-агента на GitHub.

---

## 7. Критерии приемки прототипа

1. Система собирается и запускается без ошибок в контейнерной среде.
2. Эндпоинты проверки работоспособности (`/health`, `/health/ready`) возвращают успешный ответ.
3. Полный пользовательский сценарий — от отправки задачи в Telegram до получения ссылки на Pull Request — проходит без ошибок.
4. MVP считается принятым, если тесты TEST-001 — TEST-014 пройдены успешно.
