================================================================
КОРНЕВАЯ ПРИЧИНА ДВУХ PR
================================================================

Пайплайн задуман так:

  Telegram /new
    → GitHub Issue
    → назначение Copilot coding agent
    → PR + GitHub Actions
    → события обратно в оркестратор
    → Telegram (ссылка / статус)
    → (новое) /diff и /merge

Между «агент запущен» и «тесты прошли» оркестратор сам ничего
не делает. Он ждёт внешние события. Если событие не пришло,
пришло не в том формате или система врёт об успехе — job
зависает или идёт дальше по ложному сигналу.

Первый PR чинит эту слепоту и ложные сигналы.
Второй PR добавляет управление уже созданным PR из Telegram,
не превращая бота в второй GitHub-клиент.

----------------------------------------------------------------
BUG-001  P0  Пайплайн зависает после потери вебхука
Подтверждено живым прогоном 14.08.2026
----------------------------------------------------------------

ПОЧЕМУ ОШИБКА

Единственный живой двигатель прогресса — process_event().
Её вызывает только входящий GitHub webhook.

_process_state() умеет только два состояния:
  TASK_ACCEPTED  → запустить агента и остановиться
  TEST_PASSED    → пойти дальше

Всё между ними (PR создан, тесты прошли/упали, агент закончил)
в _process_state не обрабатывается. Если вебхук не дошёл
(неверный секрет, вебхук снят, GitHub не достучался, рестарт
контейнера) — job навсегда остаётся в CODING_AGENT_RUNNING.

Резерв уже написан: adapters/coding_agent/adapter.py::watch_issue().
Его никто не вызывает: ни pipeline_runner, ни lifespan.
recover_active_jobs при старте снова зовёт _process_state —
для CODING_AGENT_RUNNING / WAIT_TESTS это no-op. После
рестарта зависший job так и висит, пользователь молчит.

Живой прогон: Copilot создал PR, пользователь смержил,
бот не узнал — потому что сигнала не было.

КАК ИСПРАВИТЬ

1. Запускать watch_issue() как asyncio-задачу сразу после
   перехода в CODING_AGENT_RUNNING (ветка TASK_ACCEPTED,
   после trigger_coding_agent).
2. События из поллинга гнать в тот же process_event()
   (processed_event_ids). Тогда вебхук и поллинг на одно
   событие не обработаются дважды.
3. Если job в CODING_AGENT_RUNNING / WAIT_TESTS дольше
   порога (дефолт 30 минут) без единого события — написать
   пользователю «нет новостей от GitHub уже N минут,
   проверьте issue вручную: <ссылка>». Job в terminal
   не переводить: это предупреждение, не фейл.
4. В recover_active_jobs для нетерминальных job, которые
   ждут внешние события, поднимать те же watchers.

РЕШЕНИЕ

config/settings.py — пороги:

  coding_agent_stale_timeout_sec = 1800
  coding_agent_poll_interval_sec = 30
  coding_agent_poll_timeout_sec  = 21600

orchestrator/pipeline_runner.py:

  после trigger_coding_agent:
      job.state = CODING_AGENT_RUNNING
      self._ensure_watchers(job)

  _ensure_watchers(job):
      если нет живой задачи — asyncio.create_task(_run_watch_issue(job))
      плюс _run_stale_watchdog(job)

  _run_watch_issue:
      async for event in coding_agent.watch_issue(job.issue_number):
          await process_event(event)   # та же идемпотентность

  _run_stale_watchdog:
      если last_event_at старше порога и ещё не предупреждали:
          «Нет новостей от GitHub уже {N} минут, проверьте issue
           вручную: {issue_url}»
          job не менять

  process_event:
      если event_id уже в processed_event_ids — выйти
      иначе обновить job.last_event_at и сделать переход

  recover_active_jobs:
      TASK_ACCEPTED / TEST_PASSED → _process_state
      CODING_AGENT_RUNNING / WAIT_TESTS → _ensure_watchers

app/lifespan.py: при старте recover_active_jobs(); при стопе
отменить watch/watchdog задачи.

Критерий: вебхук выключен (или секрет сломан) → /new всё равно
доходит до финального Telegram за счёт поллинга. Искусственно
зависший job даёт warning, но не падает в FAILED.


----------------------------------------------------------------
BUG-002  P1  Fix-триггер шлёт неподтверждённый текст
----------------------------------------------------------------

ПОЧЕМУ ОШИБКА

Единственный путь, который оркестратор реально вызывает при
падении тестов — github.adapter.trigger_fix из
_handle_test_failure.

Он публикует:

  @{copilot_username} Please analyze the test failure log above
  and push a fix.

При текущем дефолте логина это:

  @github-copilot[bot] Please analyze...

Это не команда из GitHub Changelog (24.03.2026)
«@copilot Fix the failing tests» и не FR-4.2 проекта
«публикует команду @copilot fix the failing tests».

Произвольный текст с нестандартным упоминанием бота не обязан
запускать новую сессию агента. После красного CI пайплайн
может навсегда остаться без фикса.

КАК ИСПРАВИТЬ

Тело комментария должно начинаться ровно с
`@copilot Fix the failing tests` — упоминание продукта
@copilot, не username бота. Лог ошибки — ниже, в code block,
как контекст, не как замена команды.

РЕШЕНИЕ

Комментарий:

  @copilot Fix the failing tests

  ```
  <лог ошибки>
  ```

Делать это не в github.trigger_fix, а в уже готовом
coding_agent.trigger_fix_iteration (см. BUG-003).

Критерий: при провале CI комментарий начинается ровно с
`@copilot Fix the failing tests`; агент открывает новую
сессию и пушит фикс в ту же ветку.

При следующем ревью легко «починить» мёртвый файл и оставить

Вариант (б) — оставить github.trigger_fix и удалить мёртвый

----------------------------------------------------------------

ПОЧЕМУ ОШИБКА

Везде дефолт copilot_username = "github-copilot[bot]":

Независимые источники (GitHub discussions, git blame,

Отдельного аккаунта для комментариев нет.

(BUG-007), поэтому детекция формально жива. Но:
  — дефолт протекает в текст trigger_fix (BUG-002);
  — путает поддержку и документацию.

КАК ИСПРАВИТЬ

Один дефолт везде: copilot-swe-agent[bot].
Комментарий в issues.py заменить на факт: один логин
и для назначения, и для комментариев/PR.
Обновить .env.example и три документа, где фигурирует
github-copilot[bot].

РЕШЕНИЕ

  COPILOT_USERNAME=copilot-swe-agent[bot]

  # issues.py
  # Агент использует один логин copilot-swe-agent[bot]
  # и для назначения, и для комментариев/PR.
  # Предположение про отдельный github-copilot[bot] —
  # ошибочное, не используем.
  _COPILOT_ASSIGNEE = "copilot-swe-agent[bot]"

Критерий: grep -rn "github-copilot\[bot\]" = 0, кроме явной
пометки «ошибочное предположение, не используем».


----------------------------------------------------------------
BUG-005  P1  Назначение агента не проверяет фактический результат
----------------------------------------------------------------

ПОЧЕМУ ОШИБКА

assign_copilot делает POST /issues/{n}/assignees и считает
успехом отсутствие исключения. Тело ответа не читается.

Официальная документация GitHub: assignees могут быть
«silently ignored» — API вернёт 2xx, массив assignees
пустой, никто не назначен. Так бывает, если:
  — у токена нет прав;
  — Coding agent в репозитории выключен;
  — актор не assignable.

Пайплайн тогда пишет «Coding agent started working»,
хотя агент не стартовал. Дальше срабатывает BUG-001:
вебхуков не будет, job висит.

КАК ИСПРАВИТЬ

После POST проверить, что _COPILOT_ASSIGNEE (или алиас
из _COPILOT_ASSIGNEE_ALIASES) есть в assignees ответа.
Если нет — fallback GraphQL replaceActorsForAssignable
(схема из LIVE_RUN.md). Если и он не назначил —
ADAPTER_ERROR с понятным текстом, не AGENT_ASSIGNED.

РЕШЕНИЕ

  resp = POST .../assignees  {assignees: [copilot-swe-agent[bot]]}
  body = resp.json()
  если copilot есть в body["assignees"] → успех
  иначе GraphQL replaceActorsForAssignable
  если снова нет → raise AssignmentError(
      "GitHub принял запрос, но не назначил copilot-swe-agent[bot]. "
      "Включите Copilot coding agent и проверьте права токена."
  )

Оркестратор ловит AssignmentError → ADAPTER_ERROR + сообщение
в Telegram. В «агент работает» не переходить.

Критерий: репозиторий с выключенным Copilot / токен без прав
→ ADAPTER_ERROR, не ложный старт.

BUG-006  P1  Завершение агента без штатного сигнала GitHub
----------------------------------------------------------------

ПОЧЕМУ ОШИБКА

detect_task_completion смотрит только:
  — regex в тексте комментария;
  — закрытие issue.

Модель GitHubPullRequest не знает draft и requested_reviewers.

Официально Copilot в конце:
  снимает [WIP] / выводит PR из draft,
  добавляет пользователя в reviewers.

Это задокументированный сигнал завершения. Его нет в модели
и нет в критерии. Если агент не написал «магическую фразу»
и не закрыл issue — пайплайн не считает работу законченной,
хотя PR уже готов к ревью. Снова зависание (рядом с BUG-001).

КАК ИСПРАВИТЬ

Добавить в GitHubPullRequest:
  draft: bool
  requested_reviewers: list[GitHubUser]

В detect_task_completion основным критерием сделать:
  PR запрошен через pull_requests.get_pull_request
  и (draft == False и/или requested_reviewers непустой).

Текстовые эвристики и закрытие issue оставить как запасной
сигнал, не как единственный.

РЕШЕНИЕ

  async def detect_task_completion(...):
      if pr_number:
          pr = await github.pull_requests.get_pull_request(pr_number)
          if pr.draft is False or pr.requested_reviewers:
              return True
      if issue закрыт:
          return True
      return есть completion-текст от coding-agent логина

Критерий: финальное уведомление уходит, даже если агент
не написал «завершающий» комментарий — достаточно выхода
из draft и запроса ревью.

----------------------------------------------------------------

ПОЧЕМУ ОШИБКА

Не удалять: поллинг без вебхука этот метод как раз нужен.
per_page=10, оставить только status == "completed", взять
первый из отфильтрованных (он самый свежий завершённый).

РЕШЕНИЕ

  GET .../actions/runs?branch=...&per_page=10
  for run in workflow_runs:
      if run["status"] == "completed":
          return run
  return None

Критерий: ветка с in_progress поверх предыдущего failure
→ возвращается завершённый провальный прогон.

PR-002. PIPE-PR-001  /diff и /merge
================================================================

ПОЧЕМУ ЭТО ПРОБЛЕМА (не баг кода, а дыра в сценарии)

MVP после создания PR умеет только прислать ссылку и статус.
Пользователь не может:
  — запросить актуальный diff;
  — отдать diff другому AI на ревью;
  — инициировать merge из того же Telegram.

Без этого этапа пайплайн заканчивается ссылкой. Дальше
человек уходит в GitHub руками. ТЗ требует тонкий
control/review channel, не второй GitHub-клиент.

Целевой процесс:

  Task → Copilot → PR ── /diff  → файл в Telegram
                      └── /merge → confirmation → GitHub merge

После правок Copilot: снова /diff (новый commit), снова ревью,
потом /merge. Кэш предыдущего diff запрещён.


----------------------------------------------------------------
Общие правила, без которых фича сломается так же, как PR-001
----------------------------------------------------------------

1. GitHub — источник истины по состоянию PR и факту merge.
2. Telegram adapter не ходит в GitHub API.
   Цепочка: Telegram → Adapter → Orchestrator → GitHubPort → Adapter → API.
3. /diff и /merge работают только с PR текущей задачи.
   /merge 123 не делать — меньше шанс смержить чужой PR.
4. Отдельный Telegram FSM не создавать.
   Job остаётся источником состояния. Кнопка подтверждения
   может дать MERGE_CONFIRMATION_PENDING, но это не модель PR.
5. Авторизация Telegram не заменяет права GitHub.
6. Идемпотентность:
   /diff повторно → новый актуальный diff;
   /merge после успеха → «уже объединён», второй merge не слать.


----------------------------------------------------------------
Команда /diff
----------------------------------------------------------------

ПОЧЕМУ МОЖЕТ СЛОМАТЬСЯ

Если отдать сохранённый diff, список файлов или описание PR —
внешний ревьюер увидит устаревшее состояние после новых
коммитов Copilot. Если молча обрезать большой файл —
ревью неполное и это не видно. Если слать пустой файл —
это фальшивый артефакт.

КАК ИСПРАВИТЬ

Всегда брать актуальный unified diff с GitHub
(Accept: application/vnd.github.diff) через GitHubPort.
Не кэш, не локальный diff агента, не files-list.

РЕШЕНИЕ

Условия:
  нет PR у job     → «Для текущей задачи Pull Request ещё не создан.»
  PR closed        → «Pull Request закрыт. Актуальный diff недоступен.»
  PR merged        → «Pull Request уже объединён.»
  GitHub недоступен→ «Не удалось получить diff Pull Request.
                      Попробуйте повторить команду позже.»
  пустой diff      → файл не слать:
                      «В Pull Request нет изменений для передачи на ревью.»
  больше лимита TG → не обрезать:
                      «Diff сформирован, но его размер превышает лимит Telegram.
                       PR: <link>»
  ок               → документ PR-{n}.diff,
                      caption «PR #{n} — актуальный diff для ревью»

Ошибка отправки в Telegram не меняет состояние PR/job (PR-009).
Существующее уведомление со ссылкой на PR не заменяется.


----------------------------------------------------------------
Команда /merge
----------------------------------------------------------------

ПОЧЕМУ МОЖЕТ СЛОМАТЬСЯ

Если смержить сразу по /merge — нет явного подтверждения.
Если верить CI со экрана первого /merge — между кнопкой
и вызовом API мог появиться новый commit, CI снова running
или failure. Если при отказе GitHub перевести job в DONE —
ложный финал (симметрично BUG-005: успех без факта).
Если повторный /merge снова дернет API — неидемпотентно.

КАК ИСПРАВИТЬ

Первый /merge только показывает состояние и кнопки
[ Merge ] [ Cancel ]. Merge не выполнять.
Перед фактическим merge — заново прочитать PR и CI.
Merge только через GitHubPort.merge_pull_request.
Отказ GitHub → сообщение с причиной, job не DONE.
Повтор после успеха → «PR #{n} уже объединён.»

РЕШЕНИЕ

Первый /merge (если проверки ок):

  PR #{n}

  Status: OPEN
  CI: PASS
  PR: <link>

  Объединить Pull Request?
  [ Merge ]  [ Cancel ]

Проверки (и при /merge, и ещё раз при confirm):
  PR существует и принадлежит текущему job
  PR открыт, не merged
  обязательные GitHub Actions completed + success
  Copilot не ждёт ответа пользователя
  пользователь авторизован
  GitHub разрешает merge (mergeable / mergeable_state) —
  это окончательная проверка

Отказы:
  CI running  → «Merge пока невозможен: проверки CI ещё выполняются.»
  CI failure  → «Merge невозможен: CI завершился с ошибкой.»
  PR closed   → «PR закрыт и не может быть объединён.»
  уже merged  → «PR #{n} уже объединён.»
  нет PR      → «Для текущей задачи Pull Request ещё не создан.»
  GitHub 4xx  → «Не удалось выполнить merge PR #{n}.
                 Причина: <причина GitHub>»
               job остаётся не-DONE

Успех:
  «PR #{n} успешно объединён.

   Задача завершена.»
  ссылка на PR сохраняется
  job → существующее финальное состояние FSM (DONE)
  новую параллельную модель состояния не создавать


----------------------------------------------------------------
Интерфейсы (чтобы Telegram не пророс в GitHub)
----------------------------------------------------------------

GitHubPort (не дублировать, если уже есть близкие методы):

  get_pull_request_diff(repository, pull_request_number) -> str
  merge_pull_request(repository, pull_request_number, sha=None) -> dict

NotifierPort:

  send_document(chat_id, filename, content, caption)
  send_merge_confirmation(chat_id, job_id, text)   # кнопки Merge/Cancel

Orchestrator:

  request_diff(job_id)
  request_merge(job_id)     # только экран подтверждения
  confirm_merge(job_id, confirmed: bool)

================================================================
DEFINITION OF DONE
================================================================

Пайплайн больше не зависает молча, если вебхук потерян:
есть поллинг и предупреждение человеку.

Fix после красного CI — подтверждённая команда @copilot,
не произвольный текст на неверный логин.

Назначение, активность и завершение агента определяются
фактами GitHub (assignees, точный логин, draft/reviewers),
а не «запрос ушёл» / «в логине есть слово copilot» /
«в комментарии похожая фраза».

/diff даёт актуальный полный diff файлом.
/merge требует кнопку, заново проверяет CI/PR, идёт только
через GitHubPort, повтор безопасен, ошибки не делают ложный DONE.

Пустые заглушки и вторая реализация вебхуков удалены.
Документы и TEST-015+ обновлены.
ISSUE-001 осознан как входное требование к целевому репо.
